## 1. サービス概要

- 世界観、雰囲気の近い小説と音楽をマッチングさせるサービス
- 作品の世界観に深く浸りたい人へ、さらなる深みに

---

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

- いつ：音楽を聴きながら小説を読み終えた時
- どんな状況で：読んでいる小説と似た雰囲気の音楽を聴いている状況で
- どんな気持ちになったか：しばらくしてからまたその音楽を聴いた時、読んでいた小説の世界観、印象が鮮明に蘇ってきた。

---

### 2-2. なぜそれが「気になった」のか

- 自分の性格：音楽をよく聴き、その雰囲気やメロディへのこだわりが強い。
- 過去の経験：以前にその音楽を聴いていた時には、そこまでの強い印象を感じていなかった。
- 大切にしている価値観：作品が持つ空気感などの目に見えない価値を深く感じたいと考えている。

---

## 3. 課題の整理（表面的になっていないか）

### 3-1. 表に見えている困りごと

- 小説を読む時、音楽を聴く時に、世界観、雰囲気の近い作品を探せないこと

---

### 3-2. 本当に解決したい課題は何か

- なぜ？：既存のサービスでは、空気感や世界観などの微細なニュアンスで作品を検索できないから。
- なぜ？：音楽や書籍の配信サービスが、ジャンルや作者・年代などの属性でしか作品を分類していないから。
- なぜ？：作品の空気感、世界観といったデータを構造化する仕組みがないから。

→ 本当に解決したい課題：空気感、世界観の近い小説、音楽を見つけられず、より深い没入の機会を逃してしまっていること

---

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー

年齢設定：
  - 年齢：20代前半～30代前半
  - 理由：インターネットに親しみがあり、かつ小説や音楽を楽しむ人が多い世代であるから。

生活・状況設定：
  - 生活・状況：限られた余暇時間で、小説や音楽を楽しみたいと考えている一人暮らしの社会人
  - 理由：作品に没頭したい気持ちが強く、また、音楽を聴きながら小説を読めば、2つのコンテンツを同時に楽しむことができ、時間を有効に使えるから。

環境設定：
  - 環境：SpotifyやApple Musicなどのサービスを日常的に利用している環境
  - 理由：Line Music、Youtube MusicなどはAPIが存在せず、導入が難しいから。

---

### 4-2. 自分とユーザーの距離

- 選んだ距離感：自分自身
- 理由：自分が読書をする際に、空気感、世界観の近い音楽を探すために時間をかけているから。

### 4-3. 実際に使われる可能性について(需要・存在確認)

- まず最初に使ってくれそうな人は誰か？：自分自身及び、音楽や小説を普段から楽しんでいる友人、家族
- その人は、どんな場面でこのアプリを思い出すか？：新しい小説を読む時、好きな曲を聴きながら読みたい本を探したくなった時
- 今の生活の中で、代わりに使っているものは何か？：Spotifyのプレイリスト検索や、Amazonなどのサービスなどでのタイトル検索
- それを置き換えてまで使う理由はあるか？：単語検索では見つからない、細かな空気感、世界観の近い作品を見つけられるため、使う価値はある。

## 4-4. ユーザーがサービスを導入して利用するまでのイメージ(導入・継続の流れ)

- どんな場面・困りごとがきっかけで、このサービスを知る・思い出すか：読書中に聴きたい音楽を探しても、雰囲気に合う曲が見つからなかった時
- 最初の一歩（登録・導入）で、ユーザーは何をする必要があるか：Webサイト上に小説または音楽のタイトルを入力する必要がある。
- 利用を続ける理由は何か？（習慣・必要性・価値）：新しい本を読み始める時、好きな曲に出会った時、そのたびにそれに合った作品を見つけられるから

## 5. 既存サービス・競合調査

### 5-1. 似たサービスの調査


- サービス名：Book Ground Music
- URL：https://book-ground-music.me
- どんなことができるか：書籍とそれに合った音楽を投稿でき、他のユーザーが投稿したものを見ることができる。

- サービス名：TasteDive
- URL：https://tastedive.com
- どんなことができるか：ユーザーが音楽、映画、ゲーム、書籍を評価でき、その作品を高評価したユーザーが気に入る可能性が高いほかの作品を提示することができる。

---

### 5-2. それでも自分が作りたい理由

- なぜ満足できなかったのか：マイナーな作品には対応しておらず、メジャーな作品でもオススメされる作品に違和感があったため。
- どこに違和感があったのか：ユーザーの人数が少ないため、違和感のある作品が表示されることが多かった。

### 5-3. 差別化を「体験価値」で表現する

- 私のアプリの差別化ポイント：どんな作品であっても、その雰囲気に合った作品を提示できること

## 6. このサービスで提供したい価値

### 6-1. ユーザーの変化

- 行動の変化：雰囲気の近い音楽、小説をすぐに見つけることができるようになる。
- 気持ちの変化：音楽と小説の互いの雰囲気をともに深く感じられるようになる。
- 考え方の変化：音楽鑑賞と読書はそれぞれ独立したものではなく、互いの印象をより深めることができるものであると考えられるようになる。

### 6-2. 価値を一文で表す

「このサービスは作品の世界観に浸りたい人が、本と音楽の相乗効果によってさらに深い没入体験を得られるようになるサービス」

## 7. このアプリで実現すること

### MVPで作る機能

- Rails 7（MVC）によるWebアプリケーションの構築
- Google Books APIを用いた書籍タイトルの検索及びデータ取得
- iTunes Search API を用いた楽曲タイトルの検索及びデータ取得
- OpenAI APIを用いた作品データの4軸パラメータ化（valence/明るさ、energy/激しさ、acousticness/素朴さ、tension/緊張度）
- 事前構築済みデータベースに対する年代でのハードフィルター及び4軸ベクトルの距離計算による類似作品抽出
- マッチング結果の表示（上位6件表示 ＋「もっと見る」ボタンでさらに表示）
- 表示楽曲のカード表示（タイトル、アーティスト名、試聴プレイヤー、Spotify・Apple Musicリンク）
- 表示書籍のカード表示（タイトル、著者名、あらすじ抜粋、Amazon商品リンク）

### 本リリースで作る機能

- React/TypeScriptを用いたフロントエンドの動的UI化
- ジャンルによるハードフィルター機能
- LocalStorageを用いた検索履歴機能
- Spotify APIを用いたSpotifyアカウント連携及びプレイリスト自動作成機能

## 8. このアプリの懸念点とその対策

### 懸念点①

- 何が問題になりそうか：事前構築するデータベース内の4軸パラメータに偏りが生じること
- なぜそう思うか：ランダムに作品を抽出すると、データがメジャーなジャンルに偏り、例外的なパラメータを持つ作品が不足すると考えられるから。
- そのために考えている対策：アンビエントやクラシック、歴史小説や実験小説などを事前に収集することで4軸の空間を満遍なく網羅できるデータ構成にする。

### 懸念点②

- 何が問題になりそうか：ユーザーが入力した書籍のデータにあらすじやジャンルが含まれていないこと
- なぜそう思うか：Google Books APIで取得したデータにはあらすじやジャンルが設定されていない場合があるため。
- そのために考えている対策：データが不足している場合は残りのデータから推論し、画面上には「あらすじ情報なし」等の注釈を表示する。

## 9. 今後の展開・発展の方向性

- 機能追加の方向性：作品からキーワードを推論し、同一のキーワードを持つ作品を抽出することで、より正確な作品を提示する。
- UI・体験の改善：SNSへのシェア機能を追加し、ユーザー数を増加させる。
- 機能以外の工夫：Amazonアソシエイトを導入し、OpenAI APIやサーバーのコストを賄うことで持続的にサービスを運営する。

## 10. 技術スタック（手段としての技術）

### 10-1. 使用予定の技術

- フレームワーク：React, TypeScript, Ruby on Rails 7
- DB：PostgreSQL
- デプロイ先：Vercel（フロントエンド）, Render（バックエンド・DB）
- 外部API：OpenAI API, Google Books API, iTunes Search API, Spotify API
- 使用予定ライブラリ：OpenAI API Client, axios, RSpec

---

### 10-2. 技術選定の比較検討

| 候補 | 採用/不採用 | 理由 |
| --- | --- | --- |
| React | 採用 | SPAを構築しやすく、コードの再利用もしやすいため |
| Next.js | 不採用 | 構成をシンプルにし、コードの複雑化を防ぐため |
| TypeScript | 採用 | 静的型付けによって4軸パラメータなどを安全に保持するため |
| Ruby on Rails 7 | 採用 | APIの開発が行いやすく、機能拡張もしやすいため |
| PostgreSQL | 採用 | 拡張性やパラメータの距離計算などに優れているため |
| MySQL | 不採用 | 拡張性やパラメータ計算においてはPostgreSQLが優れているため |
| Vercel | 採用 | Reactの画面公開やデプロイが行いやすいため |
| AWS | 不採用 | 初期設定やインフラ管理が複雑になるため |
| Render | 採用 | RailsとPostgreSQLを低コストで手軽に運用できるため |
| Heroku | 不採用 | Renderと比較して運用コストが大きくなるため |
| OpenAI API Client | 採用 | OpenAI APIを安全に利用できるため |
| axios | 採用 | エラーやデータが処理しやすく、シンプルに記述できるため |
| fetch API | 不採用 | axiosと比較してコードが複雑になるため |
| RSpec | 採用 | テストが読みやすく、仕様書としても活用しやすいため |
| Minitest | 不採用 | 記述のしやすさや使用実績においてはRSpecが優れているため |

- 今回チャレンジしたい点：OpenAI APIを活用したデータベース構築と、4軸パラメータの距離計算を用いた検索ロジックの実装
- 不安な点：初期データの事前処理実行時におけるレートリミット対策とエラーハンドリング

### 10-3. キャッチアップ不足の懸念

1. 完成までのハードルが高い
開発やエラー解決に想定以上の時間を要し、予定通りの機能を実装できない可能性がある。
2. Issueの見積もりが難しい
技術の学習に要する時間が不明瞭であるため、開発期間内に完了することが難しくなる可能性がある。
